> 최종 갱신: 2026-10-21
> 기획서: 본 게임 리포 `MalangE`의 `Docs/Game_Design.md` (비공개)

## 왜 실험부터 하나

이 게임은 시스템(머지, 토핑, 도감)이 아무리 잘 짜여 있어도 **말랑이를 만지는 게 재미없거나 오버레이가 거슬리면 성립하지 않는다.** 반대로 시스템 쪽은 Boxal에서 비슷한 걸 이미 해봤다(성장 카드 택1, UGS, 상점).
→ 위험이 큰 두 가지를 먼저 확인하고 개발에 착수한다.

### 이 프로젝트의 2대 도전과제

1. **오버레이** — 바탕화면 위에 말랑이를 띄우고, 컴퓨터를 쓰는 동안 언제든 만질 수 있게
2. **말랑이 인터랙션** — 늘리고, 찌르고, 주무르고, 던지는 손맛

### 실험 원칙

- 각 실험은 **"이걸로 뭘 결정하는지"와 통과 기준**이 있어야 한다. 결론 없이 만지작거리기만 하면 끝나지 않는다.
- **실험용 프로젝트는 본 프로젝트와 분리** — 이 리포(`MalangLab`)가 실험용, 본 게임은 `MalangE`. 실험 코드는 지저분해지기 마련이라, 결론만 가져가고 코드는 버릴 수 있어야 가볍다.
- 실험이 끝나면 이 문서의 **결과** 칸을 채우고, 결정된 내용은 기획서(`MalangE` 리포)의 "12. 미정 사항"에 반영한다.

## 도전과제 ① 오버레이

### 기술 방향 (사전 조사)

Unity 엔진 기능만으로는 안 되지만, 별도 프로그램까지는 필요 없다.

```
Unity 프로그램 하나
  Unity     → 말랑이 렌더링, 물리, 게임 로직
  Win32 API → 창 투명화, 항상 위, 클릭 통과  (C#에서 P/Invoke로 user32.dll 직접 호출)
```

| 방식 | 언제 필요한가 | 판단 |
|---|---|---|
| **Unity + P/Invoke** (UniWindowController, 오픈소스 MIT) | 투명, 항상 위, 클릭 통과, 창 위치·크기 | ✅ 기본 |
| C++ 네이티브 플러그인 DLL | C#으로 번거로운 저수준 기능 | 필요해지면 |
| 별도 도우미 프로그램 | 자동 시작, 업데이트 | 나중 |
| 다른 엔진 (Godot 4 등) | 투명 창·클릭 통과 기본 지원 | Unity 경험·Boxal UGS 코드를 버리게 됨 → 보류 |

### 미리 알고 가는 함정

- 투명 창은 **에디터에서 확인이 안 되고 빌드에서만** 보인다 → 처음부터 빌드로 테스트.
- **URP는 후처리 때문에 알파가 깨질 수 있다** → 렌더 파이프라인은 A1에서 정한다.
- Player Settings의 **DXGI 플립 모델 스왑체인** 설정이 투명 창과 충돌할 수 있다 → 첫 빌드 체크리스트.
- Windows는 창 단위로만 클릭 통과를 켜고 끌 수 있다 → **매 프레임 커서 아래가 말랑이인지 확인해 토글**해야 한다. 한 박자 늦으면 "잡으려 했는데 뒤 창이 눌리는" 문제.
- 전체화면 게임 위에는 안 뜬다 (그래야 맞는 동작).

#### A1 결과 (2026-10-20)

실험 코드: `Assets/Experiments/A_Overlay/`

**결정된 것**

| 항목 | 결론 |
|---|---|
| 렌더 파이프라인 | **URP 유지.** 단 그래픽 API를 **D3D11로 고정**해야 한다 (아래 3번) |
| UniWindowController | **필요 없다.** 직접 P/Invoke로 충분했다 (약 500줄, 의존성 0) |
| 투명 방식 | `DwmEnableBlurBehindWindow` + 빈 리전(`CreateRectRgn(0,0,-1,-1)`) |
| 클릭 통과 | `WS_EX_LAYERED \| WS_EX_TRANSPARENT`를 커서 위치에 따라 매 프레임 토글 |

**물렸던 함정 (순서대로)**

투명 하나 켜는 데 일곱 겹이 쌓여 있었다. 하나씩 벗겨내는 수밖에 없었다.

| # | 막은 것 | 어떻게 드러났나 |
|---|---|---|
| 1 | URP 에셋의 `AllowPostProcessAlphaOutput`이 꺼짐 | 알파가 아예 출력되지 않음 |
| 2 | 같은 에셋의 `PrefilterAlphaOutput`이 켜짐 | 알파 셰이더 variant가 **플레이어 빌드에서만** 걷혀 나감 |
| 3 | **그래픽 API가 D3D12 우선** | 제일 컸다. D3D12는 플립 모델 스왑체인만 쓸 수 있고, 플립 모델은 레이어드 창 색 키와 DWM 알파 합성 **둘 다**와 호환되지 않는다. `useFlipModelSwapchain=false`는 D3D11에서만 의미가 있어 무시됐다 |
| 4 | `DwmExtendFrameIntoClientArea` + 테두리 제거 | 확장할 프레임이 없어 아무 일도 안 일어남. 테두리를 켜면 Win11 글래스 재질이 끼어 하얘진다 |
| 5 | `SetWindowLong(GWL_EXSTYLE)`이 색 키를 지움 | 투명 처리를 스타일 변경 **전에** 해서 매번 덮였다 |
| 6 | 클릭 통과에 `WS_EX_TRANSPARENT`만 걺 | Windows는 `WS_EX_LAYERED`가 **함께** 있어야 히트 테스트에서 창을 빼준다 |
| 7 | 커서 위치를 `Input.mousePosition`으로 읽으려 함 | 클릭 통과가 켜진 창은 마우스 메시지를 못 받아 Unity가 커서를 모른다. `GetCursorPos`로 OS에 직접 물어야 한다 |

3번이 제일 질겼다. **색 키까지 실패한 것**이 단서였다 — 색 키는 알파와 무관한 경로인데도 막혔으니 "URP가 알파를 안 준다"로는 설명이 안 되고, 합성 경로 자체가 닫혀 있다는 쪽으로 좁혀졌다.

2번은 에디터에서는 되고 빌드에서만 깨지는 종류다. 전역 지침의 "에셋 문제는 플레이어 빌드에서만 드러난다"와 같은 모양이다.

**진단 방법 메모 — 추측보다 측정**

가산 혼합처럼 밝아지는 증상을 두고 "URP가 알파를 안 준다", "스트레이트 알파라 그렇다"로 두 번 헛짚고 셰이더를 두 번 고쳤다. 카메라를 `RenderTextureFormat.ARGB32`에 렌더해 픽셀을 읽어보니 알파가 **0 아니면 1, 반투명 픽셀 0개**였고, 두 가설 모두 기각됐다. `eval` 한 번이면 되는 측정을 빌드 두 번 뒤에 했다. **다음엔 프레임버퍼부터 읽는다.**

**남겨둔 것**

- 프리멀티플라이 패스(`Shaders/PremultiplyAlpha.shader` + `FullScreenPassRendererFeature`)는 지금은 할 일이 없다. AA를 꺼서 반투명 픽셀이 없기 때문이다. **AA를 켜면 경계에 반투명 픽셀이 생기고 그때 반드시 필요해진다.** 미리 깔아둔 것. Linear 색공간이면 sRGB로 옮겨 곱해야 한다(곱셈과 감마 인코딩은 순서를 바꿀 수 없다).
- 실험 장치 한계: `F1`로 투명 방식을 런타임에 돌리면 레이어드 창 속성이 누적 오염돼 DWM 모드가 밝아진다. 비트를 떼도 속성이 완전히 지워지지 않는 Windows 동작 때문. 깨끗한 시작에서는 정상이고, **제품은 모드를 시작 시 한 번만 정하므로 문제가 되지 않는다.** 장치를 고치려면 전환을 두 프레임에 나눠야 한다.
- 안티앨리어싱은 켜보지 않았다. 알파 경로의 변수를 줄이려고 MSAA와 AA를 모두 껐다. 경계가 각져 보이는지는 별도로 봐야 한다.
- 성능은 재지 않았다 (A4).

#### A3-1 결과 (2026-10-21) — B1 전제 확인

실험 코드: `Assets/Experiments/A_Overlay/` (`ScreenWalls`, `BlobBody`, `A3_WallContact.unity`)

A3는 두 덩어리다. **B1 결정이 걸려 있는 건 앞쪽 하나뿐이라 그것만 먼저 했다.**

| | 내용 | 필요한 것 | 상태 |
|---|---|---|---|
| A3-1 | 벽에 눌린 변형이 셰이더 수식으로 표현되나 | 에디터 Play | ✅ 통과 |
| A3-2 | 화면 끝·작업표시줄 좌표가 듀얼 모니터·배율 125/150%에서 맞나 | 빌드 | 미착수 |

**확인된 것**

B1에서 셰이더 정점 변형을 고른 근거 중 유일하게 검증되지 않았던 것 —
"벽에 눌려 납작해지는 건 수식으로 표현된다" — 이 **맞았다. B1 결정을 유지한다.**

사용자 평: "약간 어색하긴한데 납득은 돼."

**구조 — 셰이더는 벽이 뭔지 모른다**

| | 아는 것 |
|---|---|
| `ScreenWalls` | 벽이 어디인지. A3-1은 카메라 시야, A3-2는 모니터 작업 영역 |
| `BlobBody` | 몸의 위치·속도, 각 벽에 얼마나 파고들었는지 |
| 셰이더 | 평면 (normal, 거리) 과 깊이 숫자뿐 |

벽의 출처가 화면 끝이든 작업표시줄이든 나중에 다른 창의 제목 표시줄이든 셰이더는 같다.
→ **A3-2는 `ScreenWalls`만 갈아끼우면 된다.**

**변형 방식 (셰이더)**

1. 벽 너머로 나간 정점을 벽면까지 민다 → 접촉면이 평평해진다
2. 눌린 만큼 벽을 따라 옆으로 퍼뜨린다 → 부피 보존 흉내
3. 미는 걸 부드럽게 수렴시킨다 → 테두리 꺾임 제거 (아래 함정 2)

평면 두 개를 받아 모서리(화면 끝 + 작업표시줄)도 동시에 처리한다.

**물렸던 함정**

| # | 막은 것 | 어떻게 드러났나 |
|---|---|---|
| 1 | 되미는 스프링과 속도 반사를 **둘 다** 넣음 | 벽으로 들어오는 속도가 매 프레임 지워져 **눌림이 쌓이질 못했다.** 가만히 놔둬도 깊이가 0.08에서 안 늘었다. 반사는 딱딱한 물체의 처리다 — 말랑한 건 감쇠 스프링 하나면 되고 되튀김은 감쇠가 낮을 때 저절로 나온다 |
| 2 | 접촉 테두리가 조개껍데기처럼 들쭉날쭉 | 벽면까지 **딱 잘라** 밀면 테두리에 꺾임이 생기는데, 이 셰이더는 노멀을 이웃 두 점의 변형 결과로 다시 구한다. 이웃이 벽 위냐 아래냐에 따라 노멀이 튀었다. `0.5*(sd + sqrt(sd²+k²))`로 부드럽게 수렴시켜 꺾임 자체를 없앴다 |
| 3 | 첫 프레임에 네 벽에 동시에 끼임 | `BlobBody.Update`가 `ScreenWalls.LateUpdate`보다 먼저 돌아 0으로 채워진 평면을 읽었다. `Awake`에서 한 번 계산해 해결 |
| 4 | 씬에 저장된 옛 값 | 되미는 힘을 110 → 60으로 고쳤는데 깊이가 계속 0.08. `9/110 = 0.082`. **같은 날 문서에 적어둔 함정에 몇 시간 뒤 그대로 걸렸다** |

2번에서 **또 진단을 먼저 틀렸다.** "정점마다 자기 깊이로 퍼뜨려서"라고 보고 고쳤더니
모양만 나아지고 물결은 그대로였다. 기하 문제가 아니라 노멀 문제였다.

**충돌 반응 (사용자 요청으로 추가)**

"약간 어색"의 원인을 찾아보니 `BlobBody`가 접촉 평면만 넘기고 **부딪힐 때 아무것도 안 했다.**
닿는 순간 눌린 모양으로 바뀌고 그대로 멎었다. 셰이더에는 출렁임 기계가 이미 있었는데
벽 충돌에서 그걸 안 건드리고 있었다.

막 닿은 순간에만 `Impact(법선, 속도)`로 출렁임을 준다. 닿아 있는 내내 주면 벽에 붙어 떤다.
시계열로 확인:

| t | wobble | 상태 |
|---|---|---|
| 0.40 | 0.0000 | 공중 |
| 0.46 | 0.3327 | 닿는 순간 |
| 1.09 | 0.0590 | 깊이 0.02 — 튀어올랐다 |
| 1.58 | 0.0117 | 수렴 중 |

출렁임 위상은 리셋하지 않고 축도 이미 출렁이는 중이면 그대로 둔다 — B1에서 그걸
리셋했다가 클릭할 때마다 끊기는 증상을 만들었다.

**남겨둔 것**

| 항목 | 메모 |
|---|---|
| 눌림 포화 | 세게 떨어뜨리면 깊이가 상한(`maxPenetration` 0.55)에 0.2초쯤 붙어 있다. 바닥을 치고 멈춘 것처럼 보일 수 있다 |
| 가만히 있을 때 | 완전 정지다. 숨쉬기 같은 미세 움직임이 없다 — 상주형이라 더 눈에 띌 수 있다 |
| 미끄러짐 변형 | 벽을 따라 끌면 접촉면이 끌리는 방향으로 늘어나야 자연스러운데, 지금은 대칭이다 |
| A3-2 | 좌표. DPI 인식, 모니터별 배율, 작업 영역. A1처럼 함정이 여러 겹일 것으로 본다 |

#### A2 메모: 창 방식 트레이드오프

| | 전체 화면 크기 투명 창 | 말랑이 크기 작은 창 |
|---|---|---|

- 다른 창의 제목 표시줄 위에 올라타기 (Shimeji 같은 연출) — 다른 창 위치를 계속 읽어야 함. 처음엔 **화면 가장자리 + 작업표시줄만** 벽·바닥으로.

## 도전과제 ② 말랑이 인터랙션

### 반응은 층으로 쌓는다

| 층 | 내용 | 대상 |
|---|---|---|
| 1. 물리 | 출렁임, 늘어남, 복원 (질감이 탄성을 정함) | 모든 말랑이 |
| 2. 소리 | 찹찹, 뽀득, 찰박 (질감·토핑이 소리를 바꿈) | 모든 말랑이 |
| 3. 성격 행동 | 움찔, 통통 튀기, 축 늘어지기 | 성격 특성에 따라 |
| 4. 표정 | 늘리면 찡그리고 쓰다듬으면 눈이 휨 | 얼굴 토핑에 따라 |

### 꼭 지켜야 하는 조건 (기획서에서 온 것)

- **얼굴은 몸 표면에 붙어서 같이 변형**되어야 한다. 위에 따로 띄우는 스프라이트로는 볼따구의 재미(늘리면 얼굴도 같이 일그러짐)가 안 나온다.
- 얼굴 토핑은 **고정 위치 + 변형 후 복원**, 장신구 토핑은 **자유 이동 + 위치 유지**.
- 색·크기·개수가 바뀌어도 자연스러워야 한다 (틴트, 스케일, 복제).
- 입력은 **마우스** (클릭 = 찌르기, 드래그 = 늘리기, 휙 놓기 = 던지기). 손가락 촉감이 없는 만큼 소리와 출렁임으로 보충.

#### B1 결과 (2026-10-21)

실험 코드: `Assets/Experiments/B_Interaction/`

후보 둘을 한 화면에 나란히 놓고 **같은 입력 한 벌**(`BlobInputDriver`)로 번갈아 만졌다.
따로 띄워 번갈아 보면 "아까 그게 더 나았나"가 되어 비교가 성립하지 않는다.

**결정된 것**

| 항목 | 결론 |
|---|---|
| 변형 방식 | **셰이더 정점 변형** (`ShaderDeformBlob`) |
| 2D냐 3D냐 | **렌더는 3D, 변형은 화면 평면.** 아래 "질문이 틀렸다" 참조 |
| 찌르기(poke) | **뺀다.** 클릭 = 찌르기 인터랙션 자체가 손맛을 해쳤다 |
| 메시 스프링 | 버리지 않고 남겨둔다. B5(질감)에서 슬라임 계열이 필요해지면 다시 본다 |

**셋이 같은 쪽을 가리켰다**

| 축 | 판정 | 근거 |
|---|---|---|
| 겉모습 | 셰이더 | 메시 스프링은 표면이 우글거린다 |
| 캐릭터 | 셰이더 | 제3자 평: 메시는 "슬라임 같다", 셰이더가 "말랑이에 가깝다" |
| 성능 | 셰이더 | 0.0019 ms vs 0.8672 ms — **456배** |

손맛만은 메시 스프링이 낫다는 평이 있었다. 그러나 그 손맛의 정체가 **점액질**이었고,
그건 이 캐릭터가 아니다.

**캐릭터 차이는 구조에서 바로 나온다**

이게 B1의 가장 중요한 발견이다. 취향 문제가 아니라 두 방식의 구조가 다른 물건을 만든다.

- **메시 스프링**은 정점마다 독립적인 물리라 **한 군데만 움푹 들어가고 나머지는 가만히 있을 수 있다.** 그게 점액질이 하는 일이다.
- **셰이더 변형**은 수식이라 몸 전체가 한 덩어리로 같이 반응한다. 그건 속이 찬 말랑한 물건(찹쌀떡, 스트레스볼)이 하는 일이다.

그동안 셰이더의 약점으로 적어둔 **"수식으로 표현되는 모양만 나온다"가 사실은 이 캐릭터에 맞는 제약이었다.**
말랑이는 흘러내리면 안 된다.

**"2D냐 3D냐"는 질문이 틀렸다**

이 실험이 결정하기로 한 건 2D/3D였는데, 만져보니 그 질문이 두 개로 쪼개져 있었다.

| | 결론 |
|---|---|
| **렌더 차원** | 3D. 음영·입체감·반투명 몸 안의 비즈를 포기할 이유가 없다 |
| **변형 차원** | 화면 평면. 카메라가 고정이라 플레이어는 사실상 평면을 본다 |

깊이 방향으로 변형하면 "3D 물체를 3D에서 잡아당기는" 느낌이 들어 손맛과 어긋난다는 평이 나왔고,
양쪽 후보에 `planarDeform`(깊이 변형 억제)을 넣어 1로 두니 해결됐다.
→ **사전 판단표의 "3D vs 2D 소프트바디" 구도는 이 구분을 못 하고 있었다.** B2 이후에도 이 구분을 유지한다.

**숫자 (642정점, 60fps 기준 2 서브스텝)**

| | 메시 스프링 | 셰이더 변형 |
|---|---|---|
| 물리 | 0.6133 ms | — |
| 렌더 평활화 | 0.2359 ms | — |
| 메시 업로드 + 노멀 | 0.0180 ms | — |
| **합계** | **0.8672 ms** | **0.0019 ms** |
| **가만히 있을 때** | **0.6094 ms (그대로)** | 0.0019 ms |

상주형이라 **대기 비용**이 핵심이다. 메시 스프링은 변형량이 0이어도 정점 642개와 모서리 1920개를
매 프레임 전부 돈다(조기 종료 없음). 고칠 수는 있지만, 셰이더가 애초에 그 비용이 없다.
→ A4에서 다시 쓸 숫자.

**방식 차이로 보였던 것의 대부분은 구현 버그였다**

이번 실험에서 되풀이해 나온 패턴이다. "A 방식이 B보다 ○○하다"고 느껴진 것 중 셋이 버그였다.

| 느껴진 것 | 진짜 원인 |
|---|---|
| 셰이더가 클릭할 때마다 툭툭 끊긴다 | `Release`/`Poke`에서 `_wobblePhase = 0`으로 리셋 → `sin` 인자가 튀어 파형 전체가 순간이동 |
| 셰이더가 메시보다 프레임이 떨어진다 | **반대였다**(200배 빠름). 커서를 직접 대입해 마우스 폴링 간격과 픽셀 양자화가 그대로 드러난 것. 메시는 물리가 그 계단을 걸러주고 있었다 → 스프링 추종으로 맞춤 |
| 메시가 각지게 보인다 | 정점 수가 162(셰이더는 642). **비교 자체가 불공정했다** |

→ **체감 차이를 방식의 차이로 결론 내기 전에 구현을 의심한다.**

**뾰족하게 꼬집히지 않으려면 네 가지가 다 필요했다**

B2에서 그대로 쓸 재료다. 하나만 빠져도 점으로 꼬집힌다.

1. 잡는 반경이 충분히 넓을 것 (반지름 1인 구에 0.55는 좁다 → 1.1)
2. 가중치 감쇠가 `t*t`가 아니라 **smoothstep** (가운데가 평평해야 넓게 끌린다)
3. **모서리 강성 > 형태 기억 강성** (반대면 이웃이 제자리로 돌아가버려 잡은 데만 뽑힌다)
4. **몸 전체도 커서 쪽으로 쏠릴 것**(`bodyFollow`) — 실제로 말랑한 걸 늘리면 몸통이 따라 쏠린다

여기에 하나 더: **일정 거리 이상 끌면 몸이 커서를 따라 움직여야 한다**(`followThreshold`).
없으면 아무리 끌어도 제자리로 돌아와 "어딘가에 묶여 있는" 느낌이 든다.

**찌르기를 뺀 이유**

"클릭 = 찌르기"는 기획서의 입력 설계였는데, 만져보니 이 인터랙션의 **존재 자체가** 손맛을 해쳤다.
셰이더 쪽 `Poke`가 `_squash`를 0에서 0.22로 한 프레임에 **위치째** 바꿔 실루엣이 통째로 튀었다.
속도 충격으로 바꿔 모양을 연속으로 만든 뒤에도, 아예 끄니까 더 나았다.
→ 기획서 입력 설계에서 **클릭 = 찌르기를 재검토**할 것. 드래그와 던지기만으로도 성립한다.

**반성 — 또 엉뚱한 때에 쟀다**

A1의 "추측보다 측정"을 B1에서도 어겼다. 모양이 다르다.

- 충격을 준 **몇 초 뒤**에 변위를 재고 "물리가 안 돌고 있다"고 진단했다. 감쇠가 이미 재운 뒤였다. 사용자가 "내가 클릭하니까 되는데"로 바로잡았다.
- 우글거림의 원인을 찾을 때 **멈춘 상태**를 재고 "지그재그가 아니다"라고 판정했다. 떨림은 움직일 때 생기므로 당연히 안 잡혔다. 그 판정으로 휘어짐 저항을 한 번 넣었다 뺐다.

→ A1은 "재기 전에 추측했다"였고 B1은 **"쟀지만 엉뚱한 순간에 쟀다"**다. 측정에는 시점도 설계가 필요하다.

**셰이더로 가면서 안고 가는 비용**

| 항목 | 메모 |
|---|---|
| 변형 수식이 두 벌 | B4(장신구 부착)에 `Deform()`을 C#에도 같은 식으로 둬야 한다. 한쪽만 고치면 장신구가 표면에서 뜬다. 다만 부착점 서너 개만 계산하면 되므로 비용은 거의 없다 |
| 국소 함몰이 안 된다 | 꾹 눌러 한 군데만 움푹 들어가는 건 흉내만 낸다. 지금 기획에는 필요 없지만 B5에서 질감 폭이 좁아질 수 있다 |
| A3(벽 충돌 변형) | 평면에 눌려 납작해지는 건 수식으로 표현되므로 풀린다고 봤다. **아직 안 해봤다** |

**남겨둔 것**

- 메시 스프링의 **렌더 평활화**(Taubin). 물리는 두고 화면에 올릴 자리만 편다. 떨림 60% 감소(0.01653 → 0.00659), 의도한 변형은 98.1% 보존, 쪼그라듦 없음. 셰이더로 갔으니 지금은 쓰지 않지만 **메시 기반이 다시 필요해지면 바로 쓸 수 있다.**
- 두 후보 모두 씬에 남긴다. B5(질감 파라미터)에서 "젤리/찹쌀떡/탱탱볼을 눈 감고 구분"을 보려면 비교 대상이 있는 편이 낫다.

#### B1 메모: 2D vs 3D 사전 판단

| | 3D (메시 변형) | 2D 소프트바디 |
|---|---|---|
| 장점 | 꾹 누르면 움푹 들어가는 입체감, 반투명 몸 안의 비즈·글리터 표현 | 귀엽게 만들기 쉬움, 표정 자유로움, 가벼움 |
| 단점 | 표정 처리(텍스처 교체 / 블렌드셰이프), 변형 튜닝 시간 | 입체감 약함 |
| 사전 판단 | 단순한 형태(거의 구체) + 표면에 그린 얼굴이면 부담 적음 | 오버레이 대기 성능 면에선 유리 |

→ 사전 판단에 기대지 말고 **B1에서 직접 만져보고 결정.** A4(대기 성능) 결과도 같이 본다.

**실제 결과:** 이 표의 구도 자체가 어긋나 있었다. "3D 메시 변형 vs 2D 소프트바디"가 아니라
**렌더 차원과 변형 차원을 따로 정하는** 문제였다. 위 B1 결과 참조.
