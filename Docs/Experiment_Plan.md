# 말랑이 키우기 — 실험 계획

> 상태: 착수 전
> 최종 갱신: 2026-10-20
> 기획서: 본 게임 리포 `MalangE`의 `Docs/Game_Design.md` (비공개)

---

## 왜 실험부터 하나

이 게임은 시스템(머지, 토핑, 도감)이 아무리 잘 짜여 있어도 **말랑이를 만지는 게 재미없거나 오버레이가 거슬리면 성립하지 않는다.** 반대로 시스템 쪽은 Boxal에서 비슷한 걸 이미 해봤다(성장 카드 택1, UGS, 상점).
→ 위험이 큰 두 가지를 먼저 확인하고 개발에 착수한다.

### 이 프로젝트의 2대 도전과제

1. **오버레이** — 바탕화면 위에 말랑이를 띄우고, 컴퓨터를 쓰는 동안 언제든 만질 수 있게
2. **말랑이 인터랙션** — 늘리고, 찌르고, 주무르고, 던지는 손맛

### 실험 원칙

- 각 실험은 **"이걸로 뭘 결정하는지"와 통과 기준**이 있어야 한다. 결론 없이 만지작거리기만 하면 끝나지 않는다.
- **실험용 프로젝트는 본 프로젝트와 분리** — 이 리포(`MalangLab`)가 실험용, 본 게임은 `MalangE`. 실험 코드는 지저분해지기 마련이라, 결론만 가져가고 코드는 버릴 수 있어야 가볍다.
- 실험이 끝나면 이 문서의 **결과** 칸을 채우고, 결정된 내용은 기획서(`MalangE` 리포)의 "12. 미정 사항"에 반영한다.

## 도전과제 ① 오버레이

### 기술 방향 (사전 조사)

Unity 엔진 기능만으로는 안 되지만, 별도 프로그램까지는 필요 없다.

```
Unity 프로그램 하나
  Unity     → 말랑이 렌더링, 물리, 게임 로직
  Win32 API → 창 투명화, 항상 위, 클릭 통과  (C#에서 P/Invoke로 user32.dll 직접 호출)
```

| 방식 | 언제 필요한가 | 판단 |
|---|---|---|
| **Unity + P/Invoke** (UniWindowController, 오픈소스 MIT) | 투명, 항상 위, 클릭 통과, 창 위치·크기 | ✅ 기본 |
| C++ 네이티브 플러그인 DLL | C#으로 번거로운 저수준 기능 | 필요해지면 |
| 별도 도우미 프로그램 | 자동 시작, 업데이트 | 나중 |
| 다른 엔진 (Godot 4 등) | 투명 창·클릭 통과 기본 지원 | Unity 경험·Boxal UGS 코드를 버리게 됨 → 보류 |

### 미리 알고 가는 함정

- 투명 창은 **에디터에서 확인이 안 되고 빌드에서만** 보인다 → 처음부터 빌드로 테스트.
- **URP는 후처리 때문에 알파가 깨질 수 있다** → 렌더 파이프라인은 A1에서 정한다.
- Player Settings의 **DXGI 플립 모델 스왑체인** 설정이 투명 창과 충돌할 수 있다 → 첫 빌드 체크리스트.
- Windows는 창 단위로만 클릭 통과를 켜고 끌 수 있다 → **매 프레임 커서 아래가 말랑이인지 확인해 토글**해야 한다. 한 박자 늦으면 "잡으려 했는데 뒤 창이 눌리는" 문제.
- 전체화면 게임 위에는 안 뜬다 (그래야 맞는 동작).

### 실험 목록

| # | 실험 | 이걸로 결정하는 것 | 통과 기준 | 결과 |
|---|---|---|---|---|
| A1 | 투명 + 항상 위 + 클릭 통과 (**빌드에서**) | UniWindowController로 충분한지, **렌더 파이프라인** (Built-in / URP) | 말랑이(공) 위만 잡히고 나머지는 뒤 창이 눌림 | |
| A2 | 작은 창이 따라다니기 vs 전체 화면 크기 창 | **창 방식** | 던질 때 끊김 없음 + 대기 GPU 사용량 비교 | |
| A3 | 화면 끝, 작업표시줄 충돌 | 벽·바닥 처리 방식 | 듀얼 모니터, 배율 125%/150%에서도 위치가 맞음 | |
| A4 | 대기 성능 | 프레임 조절 전략 | 하루 켜둬도 신경 쓰이지 않는 수준 | |

#### A2 메모: 창 방식 트레이드오프

| | 전체 화면 크기 투명 창 | 말랑이 크기 작은 창 |
|---|---|---|
| 장점 | 어디로든 던질 수 있음, 구현 단순 | 가벼움 |
| 단점 | 투명 부분까지 모니터 전체를 매 프레임 렌더 → 하루 종일 켜두기엔 GPU 부담 | 던지면 창 자체가 화면 위를 따라 움직여야 함 |
| 사전 판단 | | ✅ 추천 (상주형은 리소스가 생존 조건). 던질 때만 창을 이동 |

#### 범위 밖 (나중에)

- 다른 창의 제목 표시줄 위에 올라타기 (Shimeji 같은 연출) — 다른 창 위치를 계속 읽어야 함. 처음엔 **화면 가장자리 + 작업표시줄만** 벽·바닥으로.

## 도전과제 ② 말랑이 인터랙션

### 반응은 층으로 쌓는다

| 층 | 내용 | 대상 |
|---|---|---|
| 1. 물리 | 출렁임, 늘어남, 복원 (질감이 탄성을 정함) | 모든 말랑이 |
| 2. 소리 | 찹찹, 뽀득, 찰박 (질감·토핑이 소리를 바꿈) | 모든 말랑이 |
| 3. 성격 행동 | 움찔, 통통 튀기, 축 늘어지기 | 성격 특성에 따라 |
| 4. 표정 | 늘리면 찡그리고 쓰다듬으면 눈이 휨 | 얼굴 토핑에 따라 |

### 꼭 지켜야 하는 조건 (기획서에서 온 것)

- **얼굴은 몸 표면에 붙어서 같이 변형**되어야 한다. 위에 따로 띄우는 스프라이트로는 볼따구의 재미(늘리면 얼굴도 같이 일그러짐)가 안 나온다.
- 얼굴 토핑은 **고정 위치 + 변형 후 복원**, 장신구 토핑은 **자유 이동 + 위치 유지**.
- 색·크기·개수가 바뀌어도 자연스러워야 한다 (틴트, 스케일, 복제).
- 입력은 **마우스** (클릭 = 찌르기, 드래그 = 늘리기, 휙 놓기 = 던지기). 손가락 촉감이 없는 만큼 소리와 출렁임으로 보충.

### 실험 목록

| # | 실험 | 이걸로 결정하는 것 | 통과 기준 | 결과 |
|---|---|---|---|---|
| B1 | 변형 방식 비교: **2D 소프트바디 / 3D 메시 스프링 / 셰이더 변형** | **2D냐 3D냐** | 늘렸다 놓으면 "뽀잉"이 느껴짐 | |
| B2 | 늘리기 손맛 (볼따구) | 탄성, 감쇠, 최대 늘어남 수치 | **30초 동안 계속 만지고 싶음** | |
| B3 | 얼굴이 몸 변형을 따라가기 | 얼굴 붙이는 방식 | 늘리면 얼굴도 같이 일그러지고, 놓으면 복원 | |
| B4 | 장신구 자유 이동 | 표면 미끄러짐 / 내부 부유 구현 방식 | 주무르면 밀려나고, 얼굴은 피해감 | |
| B5 | 질감 파라미터 | 질감 특성으로 낼 수 있는 차이의 폭 | 젤리, 찹쌀떡, 탱탱볼이 눈 감고도 구분됨 | |
| B6 | 속도에 따른 사운드 | ASMR 사운드 구조 | 세게 누르면 철퍽, 살살 누르면 찹 | |

#### B1 메모: 2D vs 3D 사전 판단

| | 3D (메시 변형) | 2D 소프트바디 |
|---|---|---|
| 장점 | 꾹 누르면 움푹 들어가는 입체감, 반투명 몸 안의 비즈·글리터 표현 | 귀엽게 만들기 쉬움, 표정 자유로움, 가벼움 |
| 단점 | 표정 처리(텍스처 교체 / 블렌드셰이프), 변형 튜닝 시간 | 입체감 약함 |
| 사전 판단 | 단순한 형태(거의 구체) + 표면에 그린 얼굴이면 부담 적음 | 오버레이 대기 성능 면에선 유리 |

→ 사전 판단에 기대지 말고 **B1에서 직접 만져보고 결정.** A4(대기 성능) 결과도 같이 본다.

## 추천 순서

1. **A1** (반나절~하루) — 제일 짧고, 여기서 렌더 파이프라인이 정해진다. B를 다 만든 뒤 "이 파이프라인으론 투명이 안 된다"를 알게 되면 B를 다시 해야 하므로 먼저.
2. **B1 → B2 → B3** — 핵심, 시간을 제일 많이 쓸 곳. B1에서 2D/3D가 정해지면 나머지가 따라간다.
3. **A2 ~ A4** — B 진행 중간에 쉬어가며.
4. **B4 ~ B6** — B1~B3가 재밌다는 확신이 생긴 다음.
5. **C1** 로 마무리 → 개발 착수.

## 실험이 끝나면 확정되는 것

- 2D / 3D
- 렌더 파이프라인
- 오버레이 창 방식
- 질감별 물리 파라미터 기준값
- → 이걸 바탕으로 기획서의 슬롯 상한, 고렙 표식 디자인 등 비주얼 의존 항목을 정한다.
